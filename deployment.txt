  The full lifecycle is:
  1. deploy script generates a 256-bit random committee key, deploys the Solana Anchor program to devnet and the Stellar Soroban contract to testnet, starts 3 seal nodes via docker-compose, registers observers via seal_addBridgeObserver RPC calls
  2. Seal nodes poll https://api.devnet.solana.com and https://horizon-testnet.stellar.org for lock events, mint wrapped tokens on-chain via the bridge observer set
  3. Reverse direction: burn on seal → get committee signature (HMAC or Ringtail) → claim unlock on source chain

  ---
  Answering your three questions
  
  1. Adding one extra bridge runner/node

  The seal-1/2/3 topology uses a bootstrap pattern: seal-2 and seal-3 connect to seal-1 via /dns4/seal-1/tcp/4001 (P2P). The bridge observer set is in-process — each seal node independently polls the source chains and commits deposits to its own
  local state.

  If you add a 4th node:
  - Same role as seal-2/3: bootstrap from seal-1 via --bootstrap-peers /dns4/seal-1/tcp/4001, same --bridge-committee-key, same poll intervals
  - Observation is duplicated: all 4 nodes independently poll Solana devnet and Stellar testnet. This means 4x RPC load but no shared observer state
  - No consensus required on deposits: deposits are idempotent — if multiple nodes observe the same Solana lock event, only one will succeed in process_deposit() (the BridgeDeposit is deduplicated by source_tx_hash)
  - RPC load: seal-1's RPC (:8645) is the preferred endpoint for external clients (seal-2/3 don't expose RPC ports to host in the compose file by default — you'd need to add them)

  2. Cloud deployment with encrypted local key storage

  There are currently 3 types of secrets that need protection on each node:
