# Seal DAO — Private Key & Secret Security Audit

> **Scope:** All private keys, secrets, and cryptographic material used across the Seal DAO bridge stack (local seal nodes + Solana/Stellar testnets).
>
> **Date:** 2026-05-27
>
> **Goal:** Local seal bridge nodes connecting to public testnets (Solana devnet/testnet, Stellar testnet).

## 1. Solana Deployer Key

**Path:** `~/.config/solana/id.json`
**Type:** Ed25519 keypair (64 bytes)
**Generated by:** `solana-keygen new`

### Usage
- Signs program-deploy transactions on Solana devnet/testnet/local
- Used for SOL/XLM airdrop requests (testnet)
- Owns the anchor test authority and ATA accounts

### Security Concerns
- **Testnet only:** On devnet/testnet this key has no value beyond the test SOL it holds
- **File permissions:** Default `solana-keygen` creates file with `644` permissions — world-readable private key material. Fix: `chmod 600 ~/.config/solana/id.json`
- **Exposure in logs:** The key's address appears in every transaction log; the private key itself does not

### Remediation for Production
- Use a dedicated sub-wallet or multisig wallet that never holds mainnet funds
- Consider using `solana-keygen sign` with an offline signer (e.g., Ledger) for production deployments
- Never commit this file to version control

## 2. Bridge Program Keypair

**Path:** `bridges/solana/target/deploy/seal_bridge-keypair.json` (or `programs/seal-bridge/target/deploy/`)
**Type:** Ed25519 keypair
**Generated by:** `solana-keygen new --force` (e2e script, first run)

### Usage
- Program ID derivation: the keypair's public key IS the program ID
- Upgrade authority: the Solana program is deployed via `BPFLoaderUpgradeab1e`, meaning this keypair's **public key** (not the keypair itself) becomes the upgrade authority
- The deployer key (`~/.config/solana/id.json`) is the transaction signer

### Security Concerns
- **Public key IS the program ID:** If someone can derive the private key from the public key, they could create a conflicting program at the same address
- **Keypair file contains private key:** The JSON contains all 64 bytes; if leaked, an attacker could sign transactions to upgrade the program
- **e2e script generates fresh keypair on first run:** This means the deployed program address changes between testnet runs unless the keypair is persisted

### Remediation for Production
- Use a **dedicated program keypair** generated once and persisted
- Set the upgrade authority to a **multisig wallet** or withdraw the upgrade authority after deployment
- Rotate upgrade authority away from the deployer key

## 3. Bridge Committee Key (HMAC — Testnet)

**Path:** Memory (CLI flag `--bridge-committee-key`) or `<data_dir>/bridge-committee-key.hex` (persisted)
**Type:** 32-byte hex string (used as HMAC-SHA-256 secret key)
**e2e fixture:** `[0x11; 32]` → hex `1111...1111` (64 hex chars)

### Usage
- HMAC-SHA-256(secret, message) produces the "committee signature" for withdrawal claims
- Message format: `nonce || amount || recipient || ...` (platform-specific encoding)
- Applied on **both** Solana and Seal nodes:
  - **Solana:** Anchor program recomputes HMAC and compares
  - **Seal:** Bridge observer embeds the MAC in deposit events
  - **Stellar:** Soroban contract recomputes HMAC-SHA-256 and compares

### Loading Priority (crates/seal-node/src/main.rs)
1. `--bridge-kms-config` (JSON file with KMS integration)
2. Persisted file `<data_dir>/bridge-committee-key.hex`
3. CLI flag `--bridge-committee-key` (64-char hex)

**Critical:** The persisted file is loaded **before** the CLI flag. If a prior run created `bridge-committee-key.hex`, the CLI flag is ignored. This caused committee-key fingerprint mismatches after key rotation.

### Security Concerns
- **e2e fixture is [0x11; 32]:** Trivially guessable — acceptable for local testing only
- **Shared across all 3 chains:** Same 32-byte value is used for Solana, Seal, and Stellar bridge witnesses
- **Persisted file overrides CLI flag:** After any key rotation, the `.hex` file must be deleted or the node restarted
- **Exposed in container logs:** The `--bridge-committee-key` flag value may appear in `docker logs` if verbose logging is enabled
- **No key derivation:** The raw hex bytes are used directly — no PBKDF2, no salt, no KDF

### Remediation for Production
- Use a **KMS-backed key source** (AWS KMS, HashiCorp Vault, GCP KMS)
- Generate the key with `openssl rand -hex 32` (256 bits of entropy)
- Never use the same committee key across multiple bridge pairs (Solana↔Seal vs Stellar↔Seal should have separate keys)
- Rotate the committee key periodically via `seal_bridgeRotateCommitteeKey`
- Store the persisted file with `chmod 600`
- Remove the CLI flag from docker-compose `command:` lines and use a mounted secret file instead

## 4. Bridge Committee Key (On-Chain)

**Path:** Anchor program state (PDA derived from `["bridge_state"]`)
**Type:** 32 bytes, stored on-chain

### Usage
- Stored in `BridgeState.committee_key` account field
- Visible on-chain to anyone — this is the **public** witness key

### Security Concerns
- **Public by design:** The on-chain committee key must be public for verification
- **Rotation leaves traces:** Previous committee key values remain in the on-chain state until overwritten
- **Anchor test hardcodes the key:** `tests/seal-bridge.ts` uses `new Uint8Array(32).fill(0x11)` — matches the e2e fixture but is weak for production

### Remediation for Production
- Ensure the on-chain committee key matches exactly what the witness signing infrastructure uses
- Verify the on-chain key fingerprint via `seal_bridgeGetCommitteeKeyStatus`

## 5. Ringtail Keypair

**Path:** `--bridge-ringtail-keypair-file <path>` (JSON)
**Type:** Ringtail threshold signature keypair (~16KB + 2KB JSON)
**Structure:** `{"public_params": ..., "sk_collapsed_hex": "..."}`

### Usage
- **Production witness signing:** Replaces HMAC-SHA-256 with actual threshold signature scheme
- Used by `crates/seal-bridge/src/ringtail.rs` for `sign_singleton` and `compute_committee_ringtail_sig`
- Keysource abstraction: `RingtailKeySource` trait in `keysource.rs`

### Security Concerns
- **Highest-value secret:** This key is the primary witness authority in production
- **File-based storage:** Currently only `FileKeySource` is implemented — no HSM/KMS backend
- **~18KB private key file:** Large attack surface; must be backed up for node recovery
- **Session persistence:** In-flight ringtail sessions are stored at `<data_dir>/ringtail-sessions/` — these contain ephemeral signing state
- **Singleton mode:** `ringtail-singleton` feature flag — only safe for single-validator setups

### Remediation for Production
- **Implement HSM/KMS backend** for `RingtailKeySource` trait
- Store keypair in an HSM or encrypted volume (e.g., `ecryptfs`)
- Restrict file permissions: `chmod 600 <keypair-file>`
- **Backup the keypair** — if lost, the bridge cannot produce witness signatures
- Use multi-validator mode (remove `ringtail-singleton`) for production clusters
- Monitor `<data_dir>/ringtail-sessions/` for stale sessions

## 6. Seal Validator Key

**Path:** `--validator-key <path>` or generated via `SEAL_VALIDATOR_KEY` env var
**Docker path:** `/data/validator-key.json` (mounted volume)
**Type:** ML-DSA-65 keypair (post-quantum signature)

### Usage
- Node identity on the Seal consensus network (3-body governance)
- Signs blocks via ML-DSA-65
- VRF (Verifiable Random Function) output for consensus participation
- P2P transport encryption (separate ephemeral key, not this one)

### Security Concerns
- **Volume-persisted:** Docker volume `seal-N-data` preserves the key across container restarts
- **Wiped on volume delete:** `docker compose down -v` regenerates the key — the node identity changes
- **Not shared between nodes:** Each of the 3 seal nodes has its own validator key
- **Public key is on-chain:** The validator's public key appears in the consensus committee

### Remediation for Production
- **Backup the validator key** before any `docker compose down -v`
- Map validator keys to a persistent, encrypted host path rather than anonymous Docker volumes
- Protect against accidental volume deletion in CI/CD pipelines

## 7. Seal E2E Recipient Key

**Path:** `bridges/.seal-e2e-key.json`
**Type:** ML-DSA-65 keypair (generated by `seal-cli keygen`)

### Usage
- **Wrapped token owner:** Receives wrapped SOL (wSOL) / wrapped XLM (wXLM) minted by the bridge
- **Reverse leg signer:** Burns wrapped tokens to initiate the unlock flow
- Address = SHA3-256 of the ML-DSA verifying key

### Security Concerns
- **Ephemeral test key:** Only relevant while the local stack is running
- **Persisted across runs:** The `.seal-e2e-key.json` file is reused, so the wrapped balance address is stable
- **Contains private key:** If leaked, anyone can burn the wrapped balance
- **File not in .gitignore:** Must be checked that this file is not committed

### Remediation for Production
- Never use in production — this is a test-only key
- Add `bridges/.seal-e2e-key.json` to `.gitignore`

## 8. Stellar `seal-e2e` Key

**Path:** `~/.stellar/keys/seal-e2e`
**Type:** Ed25519 keypair (generated by `stellar keys generate`)
**Network config:** `~/.stellar/networks/local.toml`

### Usage
- Soroban contract deployment and interaction
- Lock/unlock XLM operations on Stellar testnet/local
- Admin identity for the seal bridge contract (passed as `--admin` to `initialize`)

### Security Concerns
- **stellar CLI v22 vs v25:** stellar-cli v22.0.0 encodes protocol-22 XDR (rejected by protocol-25 RPC). Must use v25.x (`~/.local/bin/stellar → stellar-25`)
- **Cargo binary collision:** An old `stellar` v22 binary in `~/.cargo/bin/` can shadow the correct v25 binary if it appears first in PATH or if bash has a stale hash table entry. **Fix:** Remove `~/.cargo/bin/stellar` and run `hash -r`
- **Friendbot funding:** The key's account is funded via the friendbot endpoint — testnet only, no real value
- **Key file permissions:** `~/.stellar/` defaults to `755` — private key is world-readable

### Remediation for Production
- Set `~/.stellar/` permissions to `700` and key files to `600`
- Use a proper Stellar testnet account (funded, not friendbot) for production bridge operations
- Consider using a Soroban wallet or HD wallet for multi-account support

## 9. Network Configuration

**Path:** `~/.stellar/networks/` and `~/.config/solana/cli/config.yml`
**Type:** Network endpoint URLs and passphrases (not cryptographic secrets)

### Security Concerns
- **Solana config:** `solana config set --url <endpoint>` modifies the CLI config — the script does this for localnet, devnet, testnet
- **Stellar network config:** `stellar network add local` creates TOML with RPC URL and network passphrase
- **Not secrets:** Network configs are public information

### Remediation for Production
- Ensure the correct network is configured before running bridge operations
- Devnet vs testnet confusion can cause transactions to be submitted to the wrong chain

### Remediation for Production

## 11. P2P Transport Key

**Path:** Memory only (generated at process startup)
**Type:** ML-KEM-768 keypair (post-quantum key encapsulation)
**Module:** `crates/seal-p2p/src/pq_encrypt.rs`

### Usage
- Intra-node encrypted communication
- Fresh keypair generated per process start — not persisted

### Security Concerns
- **Ephemeral by design:** No persistent secret to protect
- **Per-start generation:** Reconnecting nodes get different keys

### Remediation for Production

## Production vs Testing Differences

| Aspect | Testing (e2e) | Production |
|--------|---------------|------------|
| Committee key | `[0x11; 32]` hardcoded | Generated random 256-bit secret via KMS |
| Signing method | HMAC-SHA-256 (host-side) | Ringtail threshold signatures |
| Validator key | Volatile Docker volume | Persistent encrypted storage |
| Solana deployer | Local keypair (devnet) | Dedicated sub-wallet or multisig |
| Stellar deployer | Friendbot-funded test account | Real testnet account with funded balance |
| Program upgrade authority | Deployer key | Multisig or withdrawn authority |
| Key rotation | Manual CLI | Governance-driven with council |

## Critical Recommendations

1. **Never use `[0x11; 32]` or any hardcoded test key in production.** The committee key must be generated with full entropy (`openssl rand -hex 32`).
2. **Implement HSM/KMS backends** for `RingtailKeySource` and `CommitteeKeySource` traits before production deployment.
3. **Back up the ringtail keypair** and validator keys before any infrastructure changes.
4. **Rotate upgrade authority** away from the Solana deployer key after program deployment.
5. **Use separate committee keys** for Solana↔Seal and Stellar↔Seal bridge pairs.
6. **Set file permissions** on all private key files to `600`.
7. **Clean stale binaries** from `~/.cargo/bin/` to prevent CLI version collisions.
8. **Remove the persisted `bridge-committee-key.hex`** after any key rotation to prevent the flag from being silently ignored.
9. **Add `.seal-e2e-key.json` and `~/.stellar/` to `.gitignore`.**
10. **Monitor Docker volumes** — `docker compose down -v` destroys validator keys and committee keys.
