### PLAN #4 — Address-validation completion (DONE)

The TODO entry was partly stale: a code audit of
`crates/seal-node/src/rpc.rs` showed
`SealAddress::from_string_encoding` was already wired into
`handle_get_balance`, `handle_faucet`, `handle_transfer`,
`handle_mint_token`, `handle_transfer_token`, and
`handle_get_token_balance`. The only remaining handler was
`seal_bridgeWithdraw` `dest_address` — which is a *foreign-chain*
address (Solana base58 / Stellar strkey), so `SealAddress` doesn't
apply directly.

Landed `seal_bridge::types::validate_dest_address(chain, addr)` in
`crates/seal-bridge/src/types.rs`:

- **Solana**: base58 alphabet (no '0', 'O', 'I', 'l') + length
  32-44 (32-byte pubkey base58-encodes to 43-44 chars; lower bound
  covers all-zeros edge case).
- **Stellar**: 56 chars total, first char 'G' (account) or 'C'
  (contract), uppercase base32 alphabet `[A-Z2-7]`.

Wired into `BridgeManager::initiate_withdrawal` so the validator
fires *before* the wrapped-balance burn — a malformed dest_address
no longer creates an unprocessable withdrawal record at the cost of
the caller's tokens.

New error variant: `BridgeError::InvalidDestAddress(String)`.

5 new tests (`crates/seal-bridge/src/bridge.rs`):

- `test_withdrawal_rejects_malformed_solana_address` — the ellipsis
  foot-gun (`"sol1recipient…"`) + asserts wrapped balance unchanged
  on rejection.
- `test_withdrawal_rejects_too_short_address` — 3-char input.
- `test_withdrawal_accepts_valid_stellar_address` — full
  deposit→withdrawal happy-path on a 56-char G-prefix strkey.
- `test_withdrawal_rejects_solana_address_for_stellar_chain` —
  cross-chain paste (32-char Solana pubkey passed to a Stellar
  withdrawal).
- `test_validate_dest_address_unit` — direct unit-tests covering
  empty, too-short, base58 forbidden chars ('0', 'O'), Stellar
  wrong-prefix, lowercase, length-55.

Format-validation only — full bs58→32-byte and Stellar CRC16
checksum verification is a follow-up that needs vendoring `bs58 0.5`
as a direct dep (it's already transitive) and a `stellar-strkey`
crate. Tracked but not mainnet-blocking; the format check already
catches the practical foot-guns.

### PLAN #6 — Alpha-bootstrap RPC auth (DONE)

Added admin gating to the bridge-bootstrap RPCs:
`seal_addBridgeObserver`, `seal_bridgeCouncilAdd/Remove`,
`seal_bridgePauseChain/Unpause`. Mainnet prerequisite.

- **`RpcConfig::admin_addresses: HashSet<String>`** — default empty.
  Populated mode requires an authorized signed caller; empty mode
  preserves the alpha-testnet bootstrap flow where `bridge-e2e.sh`
  hits these RPCs unsigned.
- **`requires_admin_auth(method) -> bool`** — pure method-name list
  of admin-gated methods.
- **`is_admin(addr, config) -> bool`** — `admin_addresses.is_empty()
  || admin_addresses.contains(addr)`.
- **Dispatch (`handle_rpc`)** — when `admin_addresses` is non-empty,
  admin methods become `requires_auth=true` (force the
  `authenticate(req)` step; `-32003` on missing/invalid sig). Then
  check `is_admin(caller_addr)`; reject with `-32004` on non-member.
  Open mode skips both checks entirely — same as before.
- **CLI** — `--admin-address sealt1…` repeatable in
  `seal-node/src/main.rs`. `--mainnet` without any
  `--admin-address` emits a startup warning ("bridge bootstrap RPCs
  callable by any unsigned client"); doesn't refuse to start because
  there are legitimate single-operator dev configs that intentionally
  run open.
- **Pause/unpause** — admin gating is *additive* to the existing 2/3
  Technical Council `approvers` check. Admin gates *who can drive
  the RPC*; the council check gates *what gets approved*. Both must
  pass in gated mode.

Tests in `crates/seal-node/src/rpc.rs`:

- `test_requires_auth` (extended) — admin methods are NOT in
  `requires_auth` itself (so testnet open mode works unsigned).
- `test_requires_admin_auth` (new) — list-membership for the 5
  gated methods, plus negative for `seal_bridgeListPaused`,
  `seal_bridgeCouncilList`, `seal_listBridgeObservers` (read-only),
  and `seal_bridgeWithdraw` (regular signed-caller, not admin).
- `test_is_admin_open_mode` — empty set lets every caller through,
  including the unsigned-fallback empty string.
- `test_is_admin_gated_mode` — populated set rejects non-members
  and the empty string.

`seal-node --lib` test count: 220 (was 217). +3 from this PR.

SPEC.md §5.5 ("Bridge bootstrap RPC authorization") documents the
gating model end-to-end: error codes, open vs gated mode, the
admin/council distinction, and the rotation path.

### PLAN #7 — Recipient-new-account policy (DONE)

Three-mode guard on `seal_transfer` + `seal_transferToken`. The
bech32m guard catches *malformed* addresses; this policy catches
*well-formed-but-unintended* addresses (typo'd-but-valid bech32m).

- **Block mode (default)** — `RpcConfig::allow_new_recipients =
  false`, request omits `confirm_new_recipient`. Reject with
  `-32007` if recipient has no prior ledger entry. The check looks
  at `BalanceStore::has_account` (or `TokenManager::has_token_account`),
  which returns true even for accounts that drained to zero — a
  known account stays known so post-spending transfers don't bounce.
- **Confirm mode (per-request)** — caller adds
  `confirm_new_recipient: true` (strict JSON boolean; `"true"` string,
  integer 1, etc. all fall back to block).
- **Allow mode (node-wide)** — `--allow-new-recipients` flag.
  Bridge nodes (mint wrapped tokens to fresh foreign-chain
  depositors) and faucet nodes (entire purpose is fresh accounts)
  set this; regular wallet-facing nodes don't.

New API surface:

- `BalanceStore::has_account(addr) -> bool` — convenience accessor;
  semantically broader than `available > 0` (as discussed above).
- `TokenManager::has_token_account(symbol, addr) -> bool` — same
  for per-token ledgers.
- `check_recipient_policy(config, params, recipient_known, addr)`
  — pure helper in `crates/seal-node/src/rpc.rs`. Reads
  `confirm_new_recipient` from params, considers
  `config.allow_new_recipients`, returns Ok or `(-32007, msg)`.

Wired into the two transfer handlers after the bech32m guard but
before the ledger mutation, so a rejected transfer never burns the
caller's balance. CLI flag in `seal-node/src/main.rs`; startup log
mentions when allow-mode is on.

Tests (`crates/seal-node/src/rpc.rs`): 6 new
`test_recipient_policy_*`:

- `block_default_rejects_new` — error code is `-32007`, message
  contains the recipient and the `confirm_new_recipient` instruction.
- `block_accepts_existing` — happy-path: known recipient, no
  confirm needed.
- `confirm_unblocks_new` — explicit per-request override.
- `confirm_false_still_blocks` — `false` is the same as omitting.
- `allow_mode_skips_check` — node-wide flag bypasses the gate.
- `non_bool_confirm_treated_as_false` — string `"true"` or int 1
  must NOT be coerced; only JSON `true` opts in.

`seal-node` test count: 226 (was 220). +6 from this PR. SPEC.md §5.6
documents the model end-to-end including the
exists-with-zero-balance subtlety.

### PLAN #3 — Seal-forms AES-GCM swap (DONE)

`examples/seal-forms/src/lib.rs` swap from XOR-stream + bespoke
HMAC-SHA3 wrapper to real `Aes256Gcm`. Spec from TODO.md
§"AES-256-GCM in examples/seal-forms" implemented end-to-end:

- **Symmetric key**: `HKDF-SHA3-256(ikm = shared_secret, salt =
  None, info = b"forms.seal/v1/aes-key")` → 32 bytes.
- **Nonce**: `SHA3-256(form_id_le || respondent_addr ||
  idx_le)[..12]` — deterministic, auditor-reconstructible.
  Uniqueness follows from `(form_id, respondent_addr, idx)` being
  unique on-chain (protocol must enforce monotonic `idx` per
  respondent or AES-GCM confidentiality breaks under nonce reuse).
- **AAD**: `form_id_le || schema_hash || respondent_addr` — binds
  the ciphertext to the form context; cross-form / cross-respondent
  replay produces a tag mismatch.
- **Cipher**: `aes-gcm = "0.10"` via `Aes256Gcm::encrypt(nonce,
  Payload { msg, aad })`. 16-byte tag appended to body.

API:

- New `pub struct AnswerContext<'a> { form_id, schema_hash,
  respondent_addr, idx }`.
- New `pub fn schema_hash(json: &str) -> [u8; 32]`
  (= `sha3_256(json)`).
- `encrypt_answer(form_pk, prev_trace, &ctx, plaintext) ->
  EncryptedAnswer` — added the `&ctx` argument.
- `decrypt_answer(form_sk, kem_ct, &ctx, answer_ct) -> Result<Vec<u8>,
  String>` — added the `&ctx` argument; now returns `Err` on tag
  mismatch (previously the XOR cipher silently returned garbage on
  wrong key).

Dropped:

- `examples/seal-forms/src/aead.rs` — bespoke HMAC-SHA3 + 15-byte
  prefix wrapper. AES-GCM bundles auth+confid; the wrapper became
  redundant.
- `xor_stream(key, data)` and `expand_block(key, counter)` in
  `lib.rs` — replaced by AES-GCM.

`main.rs` updated to construct an `AnswerContext` per response
(`idx = i`, `respondent_addr = addr`, `schema_hash` precomputed).
Demo binary runs end-to-end clean: 3 respondents, trace-walk
verifies every response, owner decrypts all three plaintexts.

Tests (7 in `lib.rs`, was 4):

- `round_trip_single_answer` — also asserts ciphertext is
  `plaintext + 16` (the GCM auth tag).
- `chain_links_three_responses` — auditor walk over the
  AEAD-bundled ciphertext (so a tag flip breaks both the tag *and*
  the chain).
- `schema_ddl_parses` — kept.
- `wrong_secret_decrypt_returns_error` — was
  `wrong_secret_decrypt_does_not_recover_plaintext`; the AEAD
  upgrade turns silent garbage into an observable error.
- `aad_drift_rejects_decrypt` (new) — same key, different
  `respondent_addr` → tag mismatch.
- `schema_drift_rejects_decrypt` (new) — `schema_hash` change
  post-submission → tag mismatch.
- `ciphertext_tampering_breaks_tag_and_chain` (new) — single-bit
  flip; assert both the AEAD tag failure and the trace-chain
  failure.
- `deterministic_nonce_matches_spec` (new) — direct check of the
  `SHA3-256(form_id_le || respondent_addr || idx_le)[..12]`
  formula so spec drift surfaces immediately.

`seal-forms` 21 tests green (lib 7 + zk_stats 4 + mpc_sum 7 + 3
others). Workspace builds clean.
