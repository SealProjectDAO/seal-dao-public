## What shipped (code)

### CLI + wallet ergonomics

- **Generic JSON-RPC passthrough** `seal rpc --method --params [--key]` — signs
  if `--key` present (via `sign_request`), plain POST otherwise. Covers every
  auth-gated handler that lacks a typed wrapper. (`crates/seal-cli/src/main.rs::run_rpc`)
- **One-shot subcommands** (all reuse `sign_request`):
  - `seal transfer <to> <amt> --node --key`
  - `seal faucet --node [--key|--address] [--amount]`
  - `seal balance --node [--key|--address]`
- **Amount parser** — accepts `50` (base units), `50.0` (SEAL), `"50 SEAL"`
  (suffix). 5 unit tests. Wired through `transfer`, `mint-token`, `faucet`
  (TUI + flat CLI). (`crates/seal-cli/src/wallet.rs::parse_amount/format_seal`)
- **Shell-quote-aware tokenizer** for the TUI REPL so
  `create-token GOLD "Gold Coin" 1000000` stops splitting `"Gold Coin"` into
  two args (previously: `name="Gold`, `max_supply=0`). 5 unit tests.
  (`crates/seal-cli/src/wallet.rs::tokenize_line`)
- **`seal keygen`** emits canonical bech32m addresses (`sealt1…`/`seal1…`),
  not the legacy hex form. Defaults to testnet; `--mainnet` flips.
  Key file JSON now includes a `network` field.
- **TUI `faucet` command** drips SEAL to the active wallet via `seal_faucet`.

### Node / RPC fixes

- **Dev faucet** — `seal-node --dev-faucet` flag + `seal_faucet` RPC
  (signature-less, per-address 24h cap = 1000 SEAL, bech32m guard). Refuses
  with `-32601 seal_faucet disabled` when the flag is off.
  (`crates/seal-node/src/rpc.rs::handle_faucet`, `main.rs`)
- **Address-derivation bug** (critical) — `authenticate()` used
  `"seal1" + hex(sha3_256(vk)[0..20])` (20 bytes, plain hex, hardcoded HRP)
  while the wallet uses `SealAddress::from_verifying_key` =
  `bech32m("sealt"|"seal", sha3_256(vk))` (32 bytes). Any signed transfer
  debited a phantom `seal1<40hex>` account with zero balance →
  `AccountNotFound`. **Fixed** — server now uses the same derivation; new
  `RpcConfig::testnet` (default true) + `seal-node --mainnet` flip flag.
- **Ghost-account burn** on transfer — `BalanceStore::transfer` did
  `accounts.entry(to).or_default()`, silently creating a ledger entry for
  any string. Sending to `sealt1recipient…` (literal ellipsis) returned
  `Status: confirmed` while the funds were effectively burned. **Fixed** —
  `handle_transfer` now runs `SealAddress::from_string_encoding(to)`
  before the ledger call. Same guard added to `handle_get_token_balance`,
  which also now rejects unknown token symbols with
  `-32602 unknown token 'X' — see seal_listTokens` instead of the
  previous permissive `{balance: 0, total_supply: 0}`.
- **SQL replay ordering** — `run_networked` in `seal-node/src/main.rs`
  always ran the demo `CREATE TABLE users + INSERT alice/bob` seed, then
  replayed the chain from disk. On restart, replay hit block 1's
  `CREATE TABLE users` against the already-seeded state and died with
  `SQL replay failed: table already exists: users`. **Fixed** — replay
  runs first; seed only executes when there's no prior chain on disk.
  Verified fresh→restart round-trip preserves state-root.

### Docker / bridge stack

- **Dockerfile** `FROM rust:1.82` → `FROM rust:1.94-bookworm`. Required
  because `vendor/risc0-groth16-5.0.0-rc.1` uses `edition = "2024"` (needs
  ≥1.85) and transitive `icu_*` 2.2.0 bumps it to ≥1.86. Matching the
  host's 1.94.1 absorbs future MSRV drift.
- **bridges/docker-compose.testnet.yml**:
  - `solana` service → added `platform: linux/amd64` (the image has no
    arm64 manifest; pin silences the warning and ensures Rosetta 2
    emulation on Apple Silicon).
  - `solana` healthcheck changed from `curl` to
    `solana cluster-version --url http://localhost:8899` — **`curl` is
    not in `solanalabs/solana:v1.18.26`**, the probe was always failing
    with `/bin/sh: 1: curl: not found`, marking the container unhealthy
    for its entire lifetime and blocking every seal-* validator waiting
    on `depends_on: solana: service_healthy`. Verified: container flips
    to `(healthy)` ~10s after recreation.
  - `stellar` — removed `--enable-horizon --enable-core` from the
    command (flags dropped upstream; quickstart now rejects them with
    `Unknown container arg`). `--local` alone starts Horizon + Core +
    friendbot. Image kept at `stellar/quickstart:latest` (the
    `:23-latest` attempted pin does not exist on Docker Hub). Commented
    `platform: linux/amd64` escape hatch left for future exec-format
    errors.

## Open bugs / security gaps surfaced (not fixed this session)

- **[security] Alpha-bootstrap bridge RPCs are unauthenticated**:
  `seal_addBridgeObserver`, `seal_bridgeCouncilAdd/Remove`,
  `seal_bridgePauseChain/UnpauseChain` are not in `requires_auth()`
  (`rpc.rs:319-347`). Anyone with RPC access can register observers
  pointing at arbitrary URLs or seat/unseat council members. Only
  `seal_bridgeWithdraw` is ML-DSA-gated. Documented in MANUAL-TESTING.md
  §17 preamble; tracked in TODOS.md. Mainnet prerequisite.
- **[code] Recipient-new-account policy** for `seal_transfer`
  (block / confirm / allow modes). Bech32m guard catches malformed
  addresses, but a well-formed-but-never-funded `sealt1…` is still
  indistinguishable from a typo. Tracked in TODOS.md.
- **[code] Address validation** not yet applied to `handle_get_balance`,
  `handle_transfer_token`, `handle_mint_token`, and bridge handlers.
- **[code] Native-balance scaling** — `BalanceStore` is still an
  in-memory `HashMap<String, Balance>`. ~150 B/entry → 10⁹ accounts ≈
  150 GB RAM. Persistent HAMT already in-tree (`seal-token/hamt.rs`)
  but not wired. Also: no state-sync, no storage rent on native
  balances, no `account_count` metric. Tracked in TODOS.md with a
  six-item work list.
- **[code] One-shot flat-CLI mutations remaining**: `seal create-token`,
  `seal mint-token`, `seal transfer-token`, **`seal set-transfer-fee`**
  (blocks §16.2), `seal place-order`/`cancel-order`, and the five
  `seal gov-*` governance mutations. Same plumbing as
  transfer/faucet/balance, different method names + param shapes.
