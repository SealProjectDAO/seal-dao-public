==== explanation ====

Blocker (a) — the signer/verifier mismatch                                                                                                           
                                                                                                                                                       
  Ringtail is a Schnorr-style identification scheme lifted to lattices. It has three things that must all agree:                                       
                                                                                                                                                       
  1. Commitment D_i that each party broadcasts in round 1                                                                                              
  2. Response z_i = r_i + c·sk_i that each party sends in round 2                                                                                      
  3. Verify equation that the on-chain verifier runs                                                                                                   
                                                                                                                                                       
  For the math to close, these three must satisfy:                                                                                                     
                                                                                                                                                       
  D = A·z − c·t          (what the verifier recomputes)                                                                                                
    = A·(r + c·s) − c·(A·s + e)                                                                                                                        
    = A·r − c·e          (cancels out s, leaves an error term)                                                                                         
                                                                                                                                                       
  So the correct commitment the signer must broadcast is D_i = A·r_i − c·e_i — or equivalently some variant involving A·r_i. The verifier then checks c
   == H(Σ D_i ‖ m).                                                                                                                                    
                                                                                                                                                       
  What seal-threshold actually does today: in crates/seal-threshold/src/ringtail.rs:228 the signer computes                                            
   
  let commitment_poly = self.ring.add(&r_i, &e_i);   // D_i = r_i + e_i                                                                                
                                                                                                                                                       
  with a comment literally saying "simplified: we use r_i + e_i directly; full implementation would do matrix-vector multiply with public A". No A·r_i 
  anywhere. So when the aggregated signature reaches verify_signature_full, the verifier recomputes A·z − c·t (which equals A·r − c·e) and hashes that,
   but the signer's challenge was computed from r + e. The two hashes don't match, verify fails.                                                       
                  
  Consequence for the BPF crate: I can't write an end-to-end test that does "sign with seal-threshold → verify with seal-ringtail-verify" because no   
  signature the signer can currently produce will pass the algebraic predicate. I proved this empirically: the test valid_signature_accepted_by_both
  failed with host verifier rejected a signature we just constructed for it, and I marked it #[ignore] with that exact reason.                         
                  
  Fix scope: add the public matrix A to RingtailParty::new, change round1 to D_i = A·r_i − c·e_i (or the paper's variant), recalibrate norm bounds,    
  re-verify the 4 Kani harnesses. Not a one-line change — you're touching the core protocol. Ought to be done with the Ringtail paper (ePrint
  2024/1113) open next to the editor.                                                                                                                  
                  
  Blocker (b) — CU measurement needs the Solana/Stellar CLIs                                                                                           
   
  Solana and Stellar contracts don't compile under plain cargo test. They target different ISAs entirely:                                              
                  
  - Solana: sbf-solana-solana target, built via cargo build-sbf (a subcommand that ships with solana-cli / Agave). Produces a .so ELF that the runtime 
  JITs to BPF bytecode. CU cost is measured by running a test transaction through solana-test-validator or bankrun and reading the consumed CU from the
   logs.                                                                                                                                               
  - Stellar: wasm32-unknown-unknown, built via cargo build --target wasm32v1-none + Soroban's optimizer. Instructions are measured by stellar contract 
  invoke --cost against stellar-core in local mode.                                                                                                    
   
  Neither toolchain is installed on this machine. cargo build -p seal-bridge from the Anchor directory fails with no matching package named            
  'anchor-lang' found because our workspace root pins [source.crates-io] replace-with = "vendored-sources" and vendor/ doesn't include the Solana crate
   stack.                                                                                                                                              
                  
  So I can write the on-chain code and I can unit-test the seal-ringtail-verify host side (which I did — 20 tests green), but I can't tell you "verify 
  consumes 412 000 CU on Solana" or "9.8 M instructions on Soroban" until a dev with solana-cli + stellar-cli runs the test programs. My 300–500K CU
  estimate for Solana is theoretical: 16 poly-muls × 3 NTTs × ~256 butterflies × ~20 CU/butterfly, plus SHA3 challenge expansion. Could be off by 2× in
   either direction.

  Why this matters before turning the feature on: Solana's per-transaction default CU budget is 200 000, and the hard ceiling is 1 400 000. If we're at
   500 000, we're fine but would have to call ComputeBudgetInstruction::set_compute_unit_limit(500_000) explicitly. If we're at 1 800 000, the verify
  never fits in a single transaction and we'd have to split it — a much bigger redesign. Measurement tells us which world we're in.                    
                  
  Fix: install solana-cli (or Agave 2.x), anchor-cli 0.30, then cd bridges/solana && anchor build && anchor test --features ringtail-verify. Same shape
   for Stellar with stellar-cli.
